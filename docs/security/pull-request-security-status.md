# Dependency repair pull requests

Dependabot's open-alert API describes the default branch. Requiring those alerts to disappear before merging the dependency repair creates a circular prerequisite. The protected branch rule remains in place; the candidate attestation evaluates those same advisory ranges against the PR's complete committed npm lock graph.

Run `scripts/security/publish-pull-request-security-status.mjs` from the exact reviewed PR head, with `GITHUB_REPOSITORY` and `PULL_REQUEST_NUMBER` set. The script reads the authenticated GitHub CLI token internally. It requires exact successful CodeQL analyses for the current PR merge commit, zero PR CodeQL alerts, zero repository secret scanning alerts, no vulnerable locked instance for any default-branch Dependabot alert, and a zero-vulnerability audit of the entire candidate dependency graph. Unsupported alert formats, manifests, ranges and unverifiable versions fail closed. Nested and aliased packages are included. The PR head and merge commit are checked again before publishing.

The resulting `Zero open security alerts` status explicitly describes the PR scope. It cannot satisfy the production release attestation, which requires a different exact description. After merge, run the existing complete security-state gate against the integrated `main` commit. Wait for Dependabot to mark the repaired alerts fixed, require all three actual alert counts to be zero, and publish the fresh main attestation before creating a release. No default-branch alert is dismissed to permit integration.

## Automatic Dependabot maintenance

`Dependabot maintenance` runs after security, dependency-review, or CodeQL workflows complete, and checks again every thirty minutes. It considers only open, non-draft Dependabot pull requests from the same repository targeting `main`. It reads each candidate's exact committed lock graph as data, applies the same candidate security matrix, and audits the graph in a temporary directory without installing dependencies or running candidate scripts. It checks the head, base, and merge revisions again before publishing the candidate-only status. GitHub then enforces the protected branch rules and the expected head when processing the squash merge. Incomplete checks, changed revisions, inaccessible security data, and rejected merges leave the pull request unmerged.

The privileged workflow loads code exclusively from `main`. It does not download pull request artefacts or check out candidate code. The `dependency-maintenance` environment admits only `main` and stores `SECURITY_READER_PRIVATE_KEY` and `SECURITY_READER_APP_ID`. The private GitHub App is installed only for this repository, with read access to contents, CodeQL, Dependabot alerts, and secret scanning alerts. The workflow creates a short-lived installation token and revokes it after use. Its separate `GITHUB_TOKEN` can publish candidate statuses and request protected merges, but the security reader cannot change code or merge pull requests. Repository policy permits that one environment secret only in this trusted workflow; other secret references remain forbidden.

After an automated merge, the workflow explicitly dispatches security CI and CodeQL for `main`, because merges authenticated with `GITHUB_TOKEN` do not trigger ordinary push workflows. This maintenance does not create a release, publish the owner-only production attestation, or install a plug-in update on a device. The production release checks and signed installation process remain separate.
